# Agents instructions for slug v3

## What is slug

slug is the Stochastically Lighting Up Galaxies code. Its purpose is to do stellar population synthesis in the regime where the total stellar mass or star formation rate are low enough that one cannot assume that the stellar mass and age distributions are well-sampled, and thus stochastic is important.

This repository is version 3 of the code. The previous version is [slug2](https://bitbucket.org/krumholz/slug2). This repository is a bottom-up rewrite, so no code is directly imported from the previous version.

## Code structure

The main top-level directories in the repository are `data`, `src`, and `tests`.

* The `data` directory contains the data files on which slug relies. See below for more details on how slug handles data files. This directory is broken into subdirectories `filters`, `imfs`, `spectra`, `tools`, and `tracks`; a further subdirectory `yields` will be added.
    * `filters` contains photometric filters
    * `imfs` contains definition files for commonly-used initial mass functions
    * `spectra` contains libraries of stellar atomsphere models that provide spectra
    * `tools` contains scripts used to download and process data from public sources and populate the other `data` directories
    * `tracks` contains stellar tracks
    * `yields` will contain libraries of stellar nucleosynthetic yields.
* The `src` directory contains the main program source code; `main.cpp` is in the top-level source directory, and the rest of the code is in subdirectories; each subdirectory defines a namespace whose name matches the name of the subdirectory, and all classes and functions defined in that subdirectory below to that namespace. The subdirectories are:
    * `core` contains the top-level routines that manage simulations and store their data
    * `extern` contains external packages slug uses
    * `feedback` will be added in the future, and will contain code for calculating stellar feedback (e.g., number of SN explosions, stellar wind power, etc.)
    * `interpolation` contains utilities for doing interpolation
    * `io` contains classes that managed IO
    * `pdfs` contains utilities for describing and managing probability distribution functions (PDFs)
    * `phot` contains code that calculates photometry
    * `pybind` contains Python bindings for the C++ code
    * `specsyn` contains code to do spectral synthesis on stars and stellar populations
    * `tracks` contains classes to manage stellar tracks
    * `utils` contains miscellaneous utilities
    * `yields` will be added in the future, and will contain functionality for calculating nucleosynthetic yields
* The `tests` directory contains unit tests. Its subdirectory structure mirrors the first-party C++ modules in `src`, with a one-to-one mapping between pieces of the source and unit tests for them, with one exception: `src/extern` (vendored third-party code) has no corresponding `tests/extern`. Subdirectories of `tests` may contain further subdirectories called `assets` that contain data files used by the unit tests; some of these assets are generated by scripts in `data/tools` (e.g. `make_powr_test_fixture.py`).

## Coding style

Most of the code is C++, with a small number of Python helper scripts. For C++ code:
* The code uses the `C++23` standard.
* Class names use `PascalCase`
* Class member variables use `camelCase_` with a trailing underscore.
* All functions, and variables that are not class members,
use `camelCase` with no trailing underscore.
* Non-void functions are always declared as `auto` with a trailing return type where necessary.
* Items should be marked `const` where possible.
* Code style is enforced by calling `clang-tidy` on all changed files in the CI, and rejecting PRs if any warnings occurs.
* Important exceptions on `clang-tidy` and style enforcement:
    * When case standards conflict with standard physics or astronomy usage, prefer physics or astronomy usage and suppress warnings with a `// NOLINT`. Example: the gravitational constant is `utils::G`.
    * Suppress `clang-tidy` warnings about only using bounds-checked container access in parts of the code where speed is important. Where a bounds check is important and there is a real chance of out-of-bounds access, instead implement the check using an `assert` so that it will be disabled when the code is built in optimized mode.
* `WarningsAsErrors` is set to `*` in `.clang-tidy`, so any warning fails the check, not just the specific categories called out above.
* CI only runs `clang-tidy` on files that changed relative to the PR's base branch (`git diff origin/<base>...HEAD`), not the whole repository. When checking your own work locally before pushing, lint against that same diff rather than the full tree.

For Python code (the `data/tools` fetch/fixture scripts and the `pybind` test suite):
* Use `snake_case` for functions and variables, matching the existing scripts.
* CLI scripts use `argparse` and lead with a short module docstring describing what the script does.

## Building

* Dependencies: CMake >= 3.15, GSL, and HDF5 (with its C++ component). OpenMP is optional; code that depends on it must guard itself with `#ifdef _OPENMP`, and the build falls back to single-threaded with a warning if no OpenMP implementation is found.
* `pybind11`, used for the Python bindings, is vendored as a git submodule under `src/extern/pybind11`. After cloning, run `git submodule update --init --recursive` before configuring, or the build will fail with missing pybind11 headers.
* The code uses C++23's `<mdspan>`, which no released version of `libstdc++` ships yet. CI builds with GCC 16+ or with Clang 18+ linked against `libc++` (not the default `libstdc++`); building with an older or default toolchain will fail to compile rather than just warn. Match one of those configurations when building locally.
* Typical configure/build:
    ```
    cmake -B build
    cmake --build build
    ```

## Testing guidelines

Testing uses `ctest`, which executes the tests defined in `tests`. There is one test executable per subdirectory of `tests`, plus a `test_PythonBindings` entry that runs the `pybind` test suite (`tests/pybind/test_bindings.py`) via `pytest` against the built extension module; `pytest` and `numpy` must be installed for whichever Python interpreter CMake picked up. Tests are labelled in `CMakeLists.txt` as either `quick` or `slow`. The `quick` tests run in a few seconds each, while the `slow` ones may take several minutes. Only the `quick` tests run in the CI because the `slow` tests require large data files that are too big to fit into a GitHub repository; they self-skip when those data files aren't present.

For any code changes that touch files in a given subdirectory of `src`, always run the tests in that subdirectory before committing or pushing changes. Use your judgement about whether additional modules are also potentially affected and should be tested. Prefer running just the relevant test target directly (e.g. build and run `slugTestPDFs`, or `ctest -R test_PDFs`) rather than the whole suite, which is slow; use `ctest -L quick` when you do want the full quick set.

## Data files

slug relies on large data sets of stellar tracks, spectral libraries, etc. that are much too large to fit in a GitHub repository. These are stored in the `data` subdirectories and may be available locally in a particular install, but are listed in `.gitignore` because they cannot go into the repository. The eventual plan, once a baseline set of large data files is established, is to host them in the ANU data commons and provide a script for users to download them.

Large data sets are stored as HDF5 files, with one or more such files in each subdirectory of `data` except `data/tools`. These are indexed by a TOML registry file whose name matches the name of the subdirectory, e.g., the index file for stellar tracks is `data/tracks/tracks.toml`.
