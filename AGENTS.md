# Agents instructions for slug v3

## What is slug

slug is the Stochastically Lighting Up Galaxies code. Its purpose is to do stellar population synthesis in the regime where the total stellar mass or star formation rate are low enough that one cannot assume that the stellar mass and age distributions are well-sampled, and thus stochastic is important.

This repository is version 3 of the code. The previous version is [slug2](https://bitbucket.org/krumholz/slug2). This repository is a bottom-up rewrite, so no code is directly imported from the previous version.

## Code structure

The main top-level directories in the repository are `data`, `slugpy`, `src`, and `tests`.

* The `data` directory contains the data files on which slug relies. See below for more details on how slug handles data files. This directory is broken into subdirectories `filters`, `imfs`, `spectra`, `tools`, and `tracks`; a further subdirectory `yields` will be added.
    * `extinct` holds tabulated extinction curves
    * `filters` contains photometric filters
    * `imfs` contains definition files for commonly-used initial mass functions
    * `spectra` contains libraries of stellar atomsphere models that provide spectra
    * `tools` contains scripts used to download and process data from public sources and populate the other `data` directories
    * `tracks` contains stellar tracks
    * `yields` will contain libraries of stellar nucleosynthetic yields.
* The `src` directory contains the main program source code; `main.cpp` is in the top-level source directory, and the rest of the code is in subdirectories; each subdirectory defines a namespace whose name matches the name of the subdirectory, and all classes and functions defined in that subdirectory below to that namespace. The subdirectories are:
    * `core` contains the top-level routines that manage simulations and store their data
    * `elem` holds fundamental elemental and atomic data
    * `extern` contains external packages slug uses
    * `extinct` contains code to handle extinction
    * `feedback` will be added in the future, and will contain code for calculating stellar feedback (e.g., number of SN explosions, stellar wind power, etc.)
    * `interpolation` contains utilities for doing interpolation
    * `io` contains classes that managed IO
    * `pdfs` contains utilities for describing and managing probability distribution functions (PDFs)
    * `phot` contains code that calculates photometry
    * `pybind` contains Python bindings for the C++ code, compiled to the `_slug` extension module that `slugpy` wraps
    * `specsyn` contains code to do spectral synthesis on stars and stellar populations
    * `tracks` contains classes to manage stellar tracks
    * `utils` contains miscellaneous utilities
    * `yields` will be added in the future, and will contain functionality for calculating nucleosynthetic yields
* The `slugpy` directory is slug's Python frontend, and the package users actually import (`from slugpy import Cluster`, etc.). Its `__init__.py` re-exports everything from `_slug`, the compiled pybind11 extension module built from `src/pybind` (see that directory's own entry above) directly into `slugpy/` by CMake, so the package's compiled and pure-Python halves live side by side with no separate install step. Pure-Python additions -- e.g. routines to read and post-process slug output files -- live in their own modules under `slugpy`.
* The `tests` directory contains unit tests. Its subdirectory structure mirrors the first-party C++ modules in `src`, with a one-to-one mapping between pieces of the source and unit tests for them, with one exception: `src/extern` (vendored third-party code) has no corresponding `tests/extern`. Subdirectories of `tests` may contain further subdirectories called `assets` that contain data files used by the unit tests; some of these assets are generated by scripts in `data/tools` (e.g. `make_powr_test_fixture.py`).

## Coding style

Most of the code is C++, with a small number of Python helper scripts. For C++ code:
* The code uses the `C++23` standard.
* Class names use `PascalCase`
* Class member variables use `camelCase_` with a trailing underscore.
* All functions, and variables that are not class members, use `camelCase` with no trailing underscore.
* Non-void functions are always declared as `auto` with a trailing return type where necessary.
* Items should be marked `const` where possible.
* Every public-facing class, method, and function gets a Doxygen-style docstring (`@file`/`@brief`/`@param`/`@return`/`@details`, as used throughout the existing code).
* Code style is enforced by calling `clang-tidy` on all changed files in the CI, and rejecting PRs if any warnings occurs.
* Important exceptions on `clang-tidy` and style enforcement:
    * When case standards conflict with standard physics or astronomy usage, prefer physics or astronomy usage and suppress warnings with a `// NOLINT`. Example: the gravitational constant is `utils::G`.
    * Suppress `clang-tidy` warnings about only using bounds-checked container access in parts of the code where speed is important. Where a bounds check is important and there is a real chance of out-of-bounds access, instead implement the check using an `assert` so that it will be disabled when the code is built in optimized mode.
* `WarningsAsErrors` is set to `*` in `.clang-tidy`, so any warning fails the check, not just the specific categories called out above.
* CI only runs `clang-tidy` on files that changed relative to the PR's base branch (`git diff origin/<base>...HEAD`), not the whole repository. When checking your own work locally before pushing, lint against that same diff rather than the full tree.

For Python code (the `data/tools` fetch/fixture scripts, the `pybind` test suite, and the `slugpy` package):
* Use `snake_case` for functions and variables, matching the existing scripts.
* CLI scripts use `argparse` and lead with a short module docstring describing what the script does.
* Every public-facing class, method, and function gets a numpy-style docstring (`Parameters`/`Attributes`/`Returns` sections, etc.). This also applies to C++ methods exposed to Python via a pybind binding (`src/pybind`): the docstring text passed to `.def(...)`/`py::init(...)` is what Python users actually see (e.g. via `help()`), so it should be numpy-style even though the C++ declaration it wraps also has its own separate Doxygen docstring -- see the `*Docstring` string_view constants already used throughout `src/pybind/Bind*.cpp` for the existing convention.
* Code in the `slugpy` package (and its tests, `tests/slugpy`) is fully type-annotated -- function/method signatures and instance attributes both -- and must pass `pyright` with zero errors or warnings; this is enforced in CI (see below) and is part of this project's code style, not optional polish. `data/tools` and the `pybind` test suite (`tests/pybind`) are not currently held to this standard and are not checked by CI's `pyright` job.
* `slugpy` and its tests must also pass `ruff check` with zero findings (default rule set, no project-specific config); this is enforced by CI's own `ruff` job, on the same changed-files basis as `pyright`/`clang-tidy` (see below). `data/tools` is not held to this standard and is not checked by CI's `ruff` job.
* `pyrightconfig.json` at the repo root pins `pythonVersion` to match what CI actually requires (independent of whichever interpreter a given editor has selected) and sets `useLibraryCodeForTypes` to `false`, since `slugpy`'s dependencies (`h5py`, `tomlkit`, `astropy`) ship no type stubs and pyright's fallback of inferring types by tracing through their untyped source is extremely noisy. One consequence: `isinstance` checks against those libraries' classes don't narrow a union the way they would against a typed library -- follow the real `isinstance` check with `typing.cast` (see `slugpy/phot_convert.py` for the established pattern) rather than fighting pyright on this.
* CI's `pyright` and `ruff` jobs, like `clang-tidy`'s, only check Python files under `slugpy`/`tests/slugpy` that changed relative to the PR's base branch, not the whole tree. Before pushing, check your own changed files the same way -- e.g. `pyright --pythonpath "$(which python3)" $(git diff --name-only origin/main...HEAD -- slugpy tests/slugpy)` -- with `pyright` built against the compiled `_slug` extension already present (`cmake --build build --target slugPython`), since every `slugpy` module imports from it. `ruff check $(git diff --name-only origin/main...HEAD -- slugpy tests/slugpy)` needs no such build step -- it's a static checker, not an import-time one.
* `_slug` ships no type stub of its own, so without one pyright treats it (and any type derived from it, e.g. a `SimControls.imf`/`.specsyn` access) as effectively untyped -- this is also why `isinstance`/`is None` narrowing against its classes sometimes doesn't stick the way it would against a typed library; reassign to a freshly, explicitly annotated local (rather than narrowing the original variable in place) when this bites. Installing [`pybind11-stubgen`](https://github.com/sizmailov/pybind11-stubgen) (`pip install pybind11-stubgen`) for whichever Python interpreter CMake picked up fixes this: `cmake` detects it at configure time and, if present, regenerates `slugpy/_slug.pyi` (gitignored -- a build artifact, one-to-one with the `_slug` binary that produced it) as a `POST_BUILD` step on `slugPython`, giving pyright/editors real signatures for most of `_slug`'s surface. Entirely optional -- `slugPython` builds and works identically without it -- but CI's `pyright` job does install it, so that job's own type checking runs against the real stub rather than treating `_slug` as untyped.

## Building

* Dependencies: CMake >= 3.15, GSL, and HDF5 (with its C++ component). OpenMP is optional; code that depends on it must guard itself with `#ifdef _OPENMP`, and the build falls back to single-threaded with a warning if no OpenMP implementation is found.
* `pybind11`, used for the Python bindings, is vendored as a git submodule under `src/extern/pybind11`. After cloning, run `git submodule update --init --recursive` before configuring, or the build will fail with missing pybind11 headers.
* The code uses C++23's `<mdspan>`. `cmake/Mdspan.cmake` picks a provider automatically, in priority order: the compiler's own native `<mdspan>` (GCC >= 16, or Clang linked against a recent `libc++`; detected with a real compile check, not a version guess), then an externally-installed `mdspan` CONFIG package (`find_package(mdspan)` -- e.g. one a cluster's module system or Spack provides, possibly a vendor-tuned build), then the Kokkos reference implementation vendored as a git submodule at `src/extern/mdspan` (run `git submodule update --init --recursive` if this path fires and the build fails with a missing-submodule error). Application code never needs to care which provider is active -- `#include <mdspan>` and `std::mdspan`/`std::extents`/`std::dextents` work unconditionally regardless. Override the auto-detection with `-DSLUG_MDSPAN_PROVIDER=NATIVE|PACKAGE|SUBMODULE` (default `AUTO`) to force a specific provider or fail loudly if it's unavailable -- useful for exercising the fallback path in CI, or getting a hard error instead of a silent fallback when a specific provider is expected.
* Typical configure/build: prefer [Ninja](https://ninja-build.org/) as the generator when it's installed (`ninja --version` to check) -- it parallelizes the build automatically and matches what CI itself uses (`CMAKE_GENERATOR: Ninja` in `.github/workflows/ci.yml`), so local builds stay closer to CI behavior and incremental rebuilds (e.g. after touching a widely-included header) are noticeably faster than with the plain-CMake default:
    ```
    cmake -S . -B build -G Ninja
    cmake --build build
    ```
    Without Ninja installed, CMake falls back to its own platform default (Unix Makefiles on Linux/macOS), which still works but builds serially by default:
    ```
    cmake -B build
    cmake --build build
    ```
    Either way, `cmake --build build [--target ...]` is the same afterward regardless of which generator configured `build/`. A build directory's generator is fixed at configure time -- switching an existing directory from Makefiles to Ninja (or back) requires wiping and reconfiguring it (`rm -rf build && cmake -S . -B build -G Ninja`), not just re-running `cmake -B build -G Ninja` in place.

## Testing guidelines

Testing uses `ctest`, which executes the tests defined in `tests`. There is one test executable per subdirectory of `tests`, plus a `test_PythonBindings` entry that runs the `pybind` test suite (`tests/pybind/test_bindings.py`) via `pytest` against the built extension module, and a `test_Slugpy` entry that runs `tests/slugpy` the same way; `pytest`, `numpy`, `h5py`, `tomlkit`, `astropy`, and `scipy` must be installed for whichever Python interpreter CMake picked up (`pyright`, too, if checking `slugpy` type-annotation compliance locally -- see the Coding style section above). Tests are labelled in `CMakeLists.txt` as either `quick` or `slow`. The `quick` tests run in a few seconds each, while the `slow` ones may take several minutes. Only the `quick` tests run in the CI because the `slow` tests require large data files that are too big to fit into a GitHub repository; they self-skip when those data files aren't present.

For any code changes that touch files in a given subdirectory of `src`, always run the tests in that subdirectory before committing or pushing changes. Use your judgement about whether additional modules are also potentially affected and should be tested. Prefer running just the relevant test target directly (e.g. build and run `slugTestPDFs`, or `ctest -R test_PDFs`) rather than the whole suite, which is slow; use `ctest -L quick` when you do want the full quick set.

## Data files

slug relies on large data sets of stellar tracks, spectral libraries, etc. that are much too large to fit in a GitHub repository. These are stored in the `data` subdirectories and may be available locally in a particular install, but are listed in `.gitignore` because they cannot go into the repository. The eventual plan, once a baseline set of large data files is established, is to host them in the ANU data commons and provide a script for users to download them.

Large data sets are stored as HDF5 files, with one or more such files in each subdirectory of `data` except `data/tools`. These are indexed by a TOML registry file whose name matches the name of the subdirectory, e.g., the index file for stellar tracks is `data/tracks/tracks.toml`.

There are also a number of smaller data files in `data`, which hold data sets small enough to be included in the repository, some of which are needed
for code operations (e.g., `data/spectra/vega.h5` holds
a spectrum of Vega needed for the Vega photometry code to function). These files are not gitignore'd.
